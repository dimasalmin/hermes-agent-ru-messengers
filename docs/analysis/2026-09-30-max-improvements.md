## Выполненные этапы

### М0. Изолированная проверка

- Получен отдельный кандидат от указанного GitHub `main`.
- Исходная регрессия воспроизведена до правок: 158 тестов проходили, но тестов на подтверждённые ошибки не было.
- Контрактный smoke запускается с настоящим Hermes и теперь проверяет `BasePlatformAdapter`, медиаметоды, lifecycle hooks и настоящий `SendResult`.
- Текущая установленная версия Hermes 0.21.4 прошла loader smoke без подключения к MAX API и без запуска модели.
- В CI добавлены обязательные pinned-проверки для Hermes 0.21.4 и `v2026.9.24`. Push ветки должен запустить workflow; результат из этого окружения не удалось прочитать (`gh` CLI отсутствует, публичный Actions API вернул 403), поэтому проход CI не заявляется.

### М1. Дефекты доставки и callbacks

- Ключ события сначала использует `update_id`, затем уникальный `callback_id`; callbacks на одном сообщении больше не объединяются по `message.mid`.
- Polling и Webhook используют общий алгоритм ключа. Миграция существующих временных SQLite тестируется на сохранение статуса и отсутствие повторного выполнения.
- Standalone/cron отправляет обычный текст без списка вложений. Если загрузка вложения не удалась, текст всё равно отправляется, а частичная ошибка возвращается явно.
- Длинная подпись к медиа разбивается на сообщения до лимита MAX; ID продолжений сохраняются.
- `send_multiple_images` возвращает настоящий Hermes `SendResult`, сохраняет ID сообщений и сообщает об ошибках отдельных элементов. Успех означает, что доставлено хотя бы одно изображение; исключение одного элемента не прекращает отправку следующих.

### М2. Очередь и жизненный цикл

- Polling только сохраняет пакет и marker в SQLite; обработка выполняется отдельно и больше не останавливает получение обновлений на время скачивания медиа.
- Есть отдельный приоритетный worker для callbacks/команд и два worker для обычных сообщений. Загрузки ограничены двумя одновременно и одной на физический чат; для одного session key передача в Hermes сериализуется.
- Состояния inbox: `pending` → `dispatching` → `accepted` → `processing` → `processed`, либо `failed`/`unknown`.
- MAX update key переносится в metadata `MessageEvent`; штатные `on_processing_start` и `on_processing_complete` Hermes обновляют состояние фоновой задачи.
- При штатной остановке и при восстановлении после перезапуска неоднозначные in-flight события помечаются `unknown`. Автоматического повтора нет.
- Команда `/maxstatus` показывает новые состояния без сообщений, секретов и URL.

### М3. Вложения

- Существующие исходящие пути сохраняют кириллическое имя, подписи и результат доставки. Ошибка одной картинки не теряет последующие.
- Максимум одного файла составляет ровно 50 000 000 байт; изображения дополнительно ограничены 7680 пикселями по каждой стороне. Сеть медиа не получает bot-token. Одновременные загрузки ограничены.
- При частичной отправке пользователь получает отдельное русское сообщение с номерами недоставленных изображений либо количеством ошибок загрузки/отправки для набора вложений.
- При явно распознанном ответе MAX о неподдерживаемом аудиоформате на загрузке или отправке исходный файл повторно загружается и отправляется как документ. Это работает и в обычных ответах, и в standalone/cron; пояснение доставляется по-русски, перекодирования нет. Длинная подпись сохраняется при повторе.
- Для проверки размеров используется Pillow; HEIC-декодер `pillow-heif` добавлен в зависимости проекта и подключается без преобразования исходного файла.
- Контракт MAX media и тесты существуют на стороне клиента/адаптера; эта работа не подтверждает доставку на телефон, разбор файла моделью, STT/TTS или доступность CDN без VPN.

Ограничение: действующий Hermes media-cache принимает байты, поэтому клиент ограничивает размер и читает тело порциями, но собирает файл в ограниченный буфер до передачи штатному cache API. Потоковая запись напрямую в Hermes cache в этом кандидате не реализована: у используемого публичного API Hermes нет файлового cache-входа. Плагин не обходит cache API и не меняет Hermes core ради этой оптимизации. Пиковое использование памяти на границе 50 000 000 байт остаётся предметом измерения. Для HEIC проверка размеров использует `pillow-heif`; live-приёмка HEIC на устройствах не выполнялась.

### М4. Управление и группы

- Меню MAX и список команд сохраняются; список зависит от registry конкретной версии Hermes.
- Ответ именно на сообщение бота распознаётся как обращение в группу. Разрешения чата и отправителя проверяются независимо; контекст по участникам остаётся раздельным.
- Кнопки по-прежнему одноразовые, ограничены чатом, пользователем и сроком жизни; live-групповая проверка не выполнялась.

### М5. Установка и наблюдение

Не выполнено и не должно выполняться до приёмки: live-проверки на телефоне и через MAX API, подтверждение результата GitHub Actions, резервная копия/тест восстановления рабочих конфигурации и SQLite, переключение symlink, рестарт production и 48-часовое наблюдение. Текущий кандидат не установлен на действующий канал.

### М6. Webhook

- При подписке проверяется HTTPS, стандартный порт 443 и отсутствие private/loopback IP literal.
- ASGI ingress сохраняет событие в общей SQLite до HTTP-подтверждения. Hermes обрабатывает durable inbox.
- В текущей конфигурации нет подтверждённого публичного HTTPS/443 ingress. Поэтому Webhook не подписывался, `MAX_WEBHOOK_URL` не задан и polling не переключался. Настройка конкретного адреса, TLS и reverse proxy остаётся отдельным инфраструктурным этапом.

## Проверки

Перед публикацией повторить и записать результаты:

```powershell
python -m pytest -q -p no:cacheprovider
python -m compileall -q plugins/max tests scripts
python scripts/max_loader_smoke.py --hermes-root <путь-к-Hermes>
```

Последняя команда должна запускаться против реального установленного Hermes; отсутствие Hermes не является успешной контрактной проверкой. Live-проверки MAX выполнять только тестовым ботом либо в согласованное окно с единственным получателем событий. Не запускать прямой polling smoke параллельно с работающим gateway.

## Приёмка перед выпуском

1. Пройти полный pytest и оба pinned Hermes contract jobs.
2. Проверить входящие и исходящие JPG/PNG, PDF/DOCX/XLSX/TXT, OGG/MP3 и MP4; попросить агента использовать контрольное содержимое, а не только проверить наличие локального файла.
3. Проверить 50 000 000 байт, превышение, несколько вложений, подписи, кириллицу, исходное изображение как документ и воспроизведение видео.
4. Проверить команды/callbacks во время медленной загрузки, повторы событий, перезапуск с `unknown`, запреты доступа и отсутствие секретов в логах.
5. На телефоне проверить меню, кнопки и каждый тип вложения; отдельно проверить API, CDN и модельный провайдер без VPN.
6. До переключения сделать и восстановить резервную копию конфигурации и SQLite, проверить Telegram, затем провести 48 часов наблюдения.
7. Webhook принимать отдельно: готовый HTTPS/443, доверенный сертификат, быстрый durable ACK, подписка MAX и восстановление. Не включать polling одновременно.

Успешный unit-тест, HTTP 200, `service active` или загрузка файла в Hermes cache по отдельности не являются приёмкой.

## Фактические результаты локальной проверки

Проверки выполнены для текущего кандидата 30 сентября 2026 года:

- `python -m pytest -q -p no:cacheprovider` — **191 пройден, 1 пропущен**. Проверка HEIC пропущена в Windows Python: в нём нет `pillow-heif`; в установленном Hermes 0.21.4 зависимость есть, проверка размеров созданного в памяти HEIC прошла отдельно.
- `python -m compileall -q plugins/max tests scripts` — завершилась без ошибок.
- `git diff --check` — замечаний по пробелам и конфликтным маркерам нет.
- Loader smoke на установленном Hermes 0.21.4 — пройдены импорт плагина, создание адаптера, настоящий `SendResult`, continuation IDs и lifecycle hooks; записи в Hermes core нет.
- Тесты аудио fallback проверяют обе точки отказа MAX (загрузка и отправка), сохранение исходного документа, пояснение и длинную подпись. Сам MAX API этими тестами не вызывается.
- В установленном Hermes 0.21.4 уже доступны Pillow и `pillow-heif`; синтетический HEIC, созданный в памяти, прошёл проверку размеров `(320, 240)`. Установка пакетов в рабочее окружение не выполнялась.
- `plugin.yaml` разбирается как YAML.

Не подтверждены: результаты GitHub Actions для закреплённых версий Hermes, живые вызовы MAX API с медиа, приёмка на телефоне, проверка содержимого файлов моделью, проверка мобильных CDN без VPN, восстановление production SQLite и переключение production. Эти пункты остаются воротами этапа М5; Webhook отдельно заблокирован отсутствием готового HTTPS/443 адреса.
